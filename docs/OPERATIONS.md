# Эксплуатация: запуск, мониторинг, резервные копии, смена семестра

Всё ниже проверено на локальной копии боевой конфигурации (`compose.prod.yml`), кроме двух вещей, которые можно проверить
только на настоящем сервере: выпуск HTTPS-сертификата и работа GitHub Actions.

## 1. Что нужно для запуска

| Что | Зачем |
|---|---|
| Сервер (VPS или машина университета) с Docker и Docker Compose | всё остальное ставится из образов |
| Доменное имя, указывающее на сервер; открытые порты 80 и 443 | прокси сам получает и продлевает HTTPS-сертификат |
| Два секрета: пароль базы и токен администратора | задаются в `.env`, в репозиторий не попадают |
| Внешний монитор доступности (например UptimeRobot, бесплатный тариф) | присылает вам сообщение, если расписание перестало обновляться |
| Место для копий базы вне сервера (другая машина, облачное хранилище) | копия на том же диске не спасёт от потери диска |

## 2. Первый запуск

```bash
git clone <адрес репозитория> vsuet-schedule && cd vsuet-schedule
cp .env.example .env
# заполнить .env: DOMAIN, DB_PASSWORD (openssl rand -base64 24), VSUET_ADMIN_TOKEN (openssl rand -hex 32)
docker compose -f compose.prod.yml up -d --build
```

Через минуту: `https://<домен>/api/v1/faculties` отдаёт 7 факультетов. Приложение само импортирует все файлы при старте
(`vsuet.import.run-on-startup=true` в профиле `prod`), вручную ничего запускать не нужно. Дальше импорт идёт каждый час.

Что видно снаружи (проверено): `/api/v1/**` (приложение для студентов), `/actuator/health/imports` (для монитора). Всё
остальное (другие адреса actuator, Swagger, корень сайта) отвечает 404. Порты приложения и базы наружу не открыты.
Административное API (`/api/v1/admin/**`) доступно только с заголовком `Authorization: Bearer <VSUET_ADMIN_TOKEN>`; если токен
в `.env` пустой, оно полностью выключено.

## 3. Мониторинг: узнать о поломке раньше студентов

Один адрес для монитора: **`https://<домен>/actuator/health/imports`**. Код 200 = расписание обновляется, код 503 = нет.
Настройте в мониторе проверку каждые 5 минут и оповещение на вашу почту или в Telegram.

Адрес краснеет, если:
- какой-то включённый файл не импортировался успешно дольше 6 часов (сайт университета недоступен, файл повреждён, структура
  файла изменилась, остановился планировщик). Порог: `vsuet.import.health-max-age`;
- файл привязан к уже закончившемуся семестру, а новый начался (забытая перепривязка при смене семестра, см. раздел 5);
- файл ни разу не импортировался.

Расписание в этих случаях **остаётся доступным** (неудачный импорт ничего не портит), поэтому это сигнал «разберитесь», а не авария.
Какой именно файл виноват, видно так:

```bash
curl -s -H "Authorization: Bearer $TOKEN" https://<домен>/api/v1/admin/sources     # у каждого файла: последний импорт
curl -s -H "Authorization: Bearer $TOKEN" https://<домен>/api/v1/admin/sources/<id>/runs
curl -s -H "Authorization: Bearer $TOKEN" https://<домен>/api/v1/admin/import-runs/<runId>/diagnostics   # что нашёл парсер
```

Состояние самого контейнера: `docker compose -f compose.prod.yml ps` (колонка STATUS показывает `healthy`).

## 4. Резервные копии и восстановление

**Что хранится в базе и что из этого нельзя потерять.** Расписание можно получить заново, повторно импортировав файлы. Нельзя
получить заново: семестры с якорем чётности, привязки файлов к семестрам, настройки источников и **идентификаторы групп**,
которые уже записаны в телефонах студентов. Поэтому копии нужны.

Сервис `backup` делает копию при запуске и затем раз в сутки (`BACKUP_INTERVAL_HOURS`), в папку `BACKUP_PATH` (по умолчанию
`./backups`), хранит 14 дней (`BACKUP_RETENTION_DAYS`). Каждая копия проверяется на читаемость до того, как заменит старую; если
свежей копии нет дольше двух интервалов, контейнер `backup` становится `unhealthy`. Потеря при аварии: не более суток. (Первая копия, сделанная в момент запуска, почти пустая: импорт ещё идёт; это нормально.)

**Копия вне сервера** (обязательна, в проект не входит, нужен ваш выбор хранилища). Например, раз в сутки с другой машины:

```bash
rsync -a --delete-after user@сервер:vsuet-schedule/backups/ /путь/к/копиям/vsuet/
```

**Восстановление** (проверено: после удаления всех данных вернулись 300 групп и 7285 занятий):

```bash
docker compose -f compose.prod.yml stop app
docker compose -f compose.prod.yml run --rm --entrypoint /bin/bash backup /ops/restore.sh /backups/vsuet-<дата>.dump
docker compose -f compose.prod.yml start app
```

Восстановление заменяет текущие данные целиком, в одной транзакции (неудачное восстановление оставляет базу как была).
Периодически, например раз в квартал, повторяйте это на копии сервера: резервная копия, из которой ни разу не восстанавливались,
ничего не гарантирует.

## 5. Смена семестра (делается дважды в год, до начала нового семестра)

Порядок важен. Он отрепетирован тестом `SemesterRolloverIntegrationTest` на всех шагах, включая обе ловушки.

1. **Когда университет выложил файлы нового семестра**, но до их импорта, зарегистрируйте семестр. Первая неделя должна быть
   понедельником и содержать первый день семестра; `firstWeekType` это чётность этой недели:

   ```bash
   curl -X POST https://<домен>/api/v1/admin/periods -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"term":"SPRING","yearFrom":2026,"startDate":"2027-02-08","endDate":"2027-06-30","firstWeekStart":"2027-02-08","firstWeekType":"NUMERATOR"}'
   ```

   Без этого шага импорт нового файла отклоняется (`PERIOD_NOT_REGISTERED`), а студенты продолжают видеть старое расписание.
   Это безопасно, но новый файл не попадёт в базу, пока вы не зарегистрируете семестр.

2. **Перепривяжите файлы, привязанные вручную** (`GET /api/v1/admin/sources`, поле `pinnedPeriodId`: сейчас это `eiu.xlsx`, оба
   файла СПО и файл заочки). Файл с неверным семестром внутри (`eiu.xlsx`) иначе продолжит писать в старый семестр:

   ```bash
   curl -X PUT https://<домен>/api/v1/admin/sources/<id>/period -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' -d '{"periodId": <id нового семестра>}'
   ```

   После перепривязки тот же файл читается заново, даже если не менялся. Если забыли: в день старта семестра
   `/actuator/health/imports` покраснеет с сообщением «re-pin it».

3. **Запустите импорт** (или дождитесь ближайшего часа): `POST /api/v1/admin/imports`. Затем проверьте `GET /api/v1/admin/sources`:
   у всех файлов последний импорт `SUCCESS`.

4. **В первый день семестра** приложение само переключается на новый семестр (текущий это последний начавшийся). Старый семестр
   в базе остаётся.

5. Если чётность недели в файлах не сходится с реальной, поправьте её: `PUT /api/v1/admin/periods/<id>`. Версия расписания всех
   групп семестра вырастет, и приложения перезагрузят расписание.

Файлы с неверным семестром или без него ведут себя так (это не меняется между семестрами): `eiu.xlsx` (неверный год в тексте),
`2-3-4_kurs.xls` и файл заочки (семестра в тексте нет) обязаны быть привязаны; остальные определяют семестр по своему тексту.

## 6. Обновление приложения и откат

```bash
git pull
docker compose -f compose.prod.yml up -d --build        # пересобирает образ; миграции базы применяются при старте
```

Перед обновлением, меняющим схему базы, сделайте копию вручную: `docker compose -f compose.prod.yml exec backup /bin/bash /ops/backup.sh`.
Откат кода: `git checkout <прошлая версия>` и тот же `up -d --build`. Если версия успела изменить схему базы, откат кода
несовместим с ней: восстановите копию, сделанную перед обновлением.

## 7. Что известно и не закрыто

- Сертификат HTTPS и GitHub Actions проверены только по конфигурации, не на живом сервере.
- Ограничения частоты запросов нет (при необходимости ставится на прокси или перед ним). Примера ограничения административного API по
  адресам закомментирован в `ops/Caddyfile`.
- Один общий админ-токен: без журнала действий и личных учёток. Достаточно для небольшой команды, для большего нужна авторизация.
- Конец осеннего семестра 2027-01-31 был предположением; подтвердите у университета и поправьте через `PUT /periods/<id>`.
